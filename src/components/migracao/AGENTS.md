# Migração Projuris

- Migração Projuris (/migracao-projuris, só admin) é separada em 5 importações (processos, tarefas, anexos, comentários, andamentos); todas registram cada item em migracoes_projuris_itens (tipo + chave_externa), que liga as rodadas entre si e permite deduplicar e 'desfazer lote'.
- Backup completo do Projuris (botão na mesma tela, modo 'backup'): recebe o zip/CSVs das ~92 tabelas, cruza pelo código interno (processonumero→cdprocesso, andamentovinculomodulo cdmodulo=3→cdprocesso, usuario→pessoa) e importa em 3 etapas independentes (processos, tarefas, andamentos), cada uma com migracoes_projuris própria e itens registrados; tarefas ligam ao processo pela tabela tarefavinculomodulo (cdmodulo 3, prioritária) ou, sem ela, pelo Relatório de Atividades do Projuris , pelos fluxos (workflowexecucao módulo 4 → workflowcontrole módulo 3) ou pela intimação de origem (tarefaevento.cdtarefa → cacheintimacaotarefa → intimacaonumeroprocesso) (Identificador TAR.x = tarefaevento.deidentificador → Processo Vinculado), soltas só quando ausentes; comentários e anexos ficam fora (sem tabela de vínculo e sem arquivos físicos), apenas contados na conferência; CSVs são lidos em Web Worker (arquivo de 152MB).- Campos específicos de relatórios de cliente (ex.: GOL Operação/Webjet/Sucessão) ficam em `processos.dados_relatorio_cliente` (jsonb) com `relatorio_origem`, exibidos na aba "Relatório do cliente" da ficha — evita criar dezenas de colunas por cliente.
- Projuris attachment imports share byte-level upload progress, bounded workers and serialized batched audit writes; this keeps transfers visible without per-file audit request overhead or unbounded memory usage.
- Projuris ZIP matching normalizes paths and Unicode, resolves consolidated parent folders by unique longest path suffix before names, and rejects ambiguity; attachment targets also use unique audited external IDs verified against existing records, so preexisting processes do not appear missing merely because their Projuris field is absent.
- Projuris task status comes from tarefaeventosituacao (situation name/behavior), never inferred from a past due date; re-running the task import reopens already-migrated tasks wrongly closed, skipping any whose status a user changed.
- Projuris tasks deleted/inactive in Projuris are imported as 'cancelado' (visible, struck through) with an auditoria_tarefas entry (acao excluida_no_projuris/inativada_no_projuris) carrying who/when from cdusuarioexclusao/dtexclusao (or last update for inactive), so history is preserved.
- Projuris workflow runs (workflowcontrole/workflowexecucao) import as workflow_execucoes of the already-imported models, audited as tipo workflow_execucao; open steps stay 'materializada' linked to the migrated task so the existing item-status sync keeps creating the next step, independent of the model's ativo flag.
- Projuris "Agenda futura" spreadsheet import (Santander Cível only) treats as hearings only the fixed lawyer-defined title list in `agendaFuturaProjuris.ts`; TAR./PRO. ids are audited in migracoes_projuris_itens (tipo tarefa/audiencia/processo) so future CSV migrations and re-runs dedupe, and comments are authored as "Importado Projuris" since Projuris exports no author.
