# Regras de arquitetura

- Process-detail task queries return original records; only the detail list expands recurring series, and shared item invalidation refreshes occurrence-status and process-side-list queries so saved occurrences display immediately without duplicate expansion.

- DJEN statistics use publication coordination before monitoring coordination for filters, membership scope and grouping, matching the listing after distribution; content-key fallback stays shared with the listing to preserve deduplication identity.

- Workflow coordination defaults reuse the user's default-coordination hook and validate it against accessible options; explicit filter choices are user-scoped and row names use the existing coordination join, avoiding new queries or permission changes.

- Projuris workflow migration selects only enabled active originals and their exact current version, audits source IDs, and imports inactive templates without executions; inherited task-type settings take precedence when requested by the export, and unresolved responsibility/checklist configuration requires review before activation.

- Kurier capture and display share a conservative body-boundary helper; only uppercase headings after compact metadata may split a body, never decision words inside prose or institutional judicial text, to prevent losing publication content.

- Unified agenda pagination uses each source's final successful response (including fallback queries) for its fullness flag, never the merged page length; all consumers use that flag because combining sources and expanding recurrences changes page length and can omit later items from office totals. Failed sources must reject the page rather than silently show incomplete totals.
- Unified agenda pages read sources sequentially (concurrency 1); parallel source reads shared mutable page state and left Painel counters empty.
- Agenda task pages filter only by the date window; recurring tasks started before it load once on page 0 and are merged by ID, because an OR on recurrence defeated the date index on every page.

- Pauta detail tabs reuse the existing Processos e Casos overview and the Judit analysis, cover, attachments and log panels; load the linked process by ID or CNJ variants only when opened, and allow cached Judit panels by CNJ without a linked process, to keep shared edits and research consistent without automatic paid queries.

- As ações Tarefa, Prazo, Evento e Audiência do botão Adicionar na ficha do processo usam `NovoItemPanel` dentro de um painel lateral direito sobreposto, mantendo o conteúdo da ficha visível ao fundo.
- Official manuals are versioned PDFs in `public/manuais`, generated by `scripts/generate_system_manuals.py` with release chapters from `scripts/manual_release_content.py`; module manuals select chapters by title through `capitulo`/`capitulos` instead of list positions so adding a release chapter cannot shift their content, and the central and module shortcuts open the same files to prevent divergent versions.
- A gestão de uma coordenação abre em `Sheet` lateral direito sobre a grade compacta; cargos em `membros_coordenacao` usam identificadores snake_case e atualizações devem confirmar a linha retornada, para impedir sucesso falso por RLS.
- Pautas extraídas dos PDFs do DEJT preservam o cabeçalho integral da sessão (linhas institucionais acima do marcador, data, hora, local e avisos), sem o cabeçalho/rodapé repetido de cada página; marcadores só iniciam blocos no começo de linha e cada processo vai da sua linha "N. Processo" até a linha do próximo, para não cortar nem misturar textos.

- Migração Projuris (/migracao-projuris, só admin) é separada em 5 importações (processos, tarefas, anexos, comentários, andamentos); todas registram cada item em migracoes_projuris_itens (tipo + chave_externa), que liga as rodadas entre si e permite deduplicar e 'desfazer lote'.
- Backup completo do Projuris (botão na mesma tela, modo 'backup'): recebe o zip/CSVs das ~92 tabelas, cruza pelo código interno (processonumero→cdprocesso, andamentovinculomodulo cdmodulo=3→cdprocesso, usuario→pessoa) e importa em 3 etapas independentes (processos, tarefas, andamentos), cada uma com migracoes_projuris própria e itens registrados; tarefas ligam ao processo pela tabela tarefavinculomodulo (cdmodulo 3, prioritária) ou, sem ela, pelo Relatório de Atividades do Projuris , pelos fluxos (workflowexecucao módulo 4 → workflowcontrole módulo 3) ou pela intimação de origem (tarefaevento.cdtarefa → cacheintimacaotarefa → intimacaonumeroprocesso) (Identificador TAR.x = tarefaevento.deidentificador → Processo Vinculado), soltas só quando ausentes; comentários e anexos ficam fora (sem tabela de vínculo e sem arquivos físicos), apenas contados na conferência; CSVs são lidos em Web Worker (arquivo de 152MB).- Campos específicos de relatórios de cliente (ex.: GOL Operação/Webjet/Sucessão) ficam em `processos.dados_relatorio_cliente` (jsonb) com `relatorio_origem`, exibidos na aba "Relatório do cliente" da ficha — evita criar dezenas de colunas por cliente.
- Envolvidos/responsáveis automáticos em itens novos vêm só de `responsaveis_fixos_tipo_tarefa` (aplicado nas telas de criação); não há trigger incluindo coordenadores, para respeitar a escolha de cada coordenação.
- App mobile é PWA só com manifest (`public/manifest.webmanifest`, sem service worker); no celular o `MainLayout` mostra `MobileBottomNav`, que abre o menu lateral pelo evento `abrir-menu-mobile`, para manter um único menu com as mesmas permissões.
- O tipo "Ata" vive em `tarefas` com `tipo_tarefa = "ATA"` e chega à agenda com `tipo = "tarefa"`; a cor própria (violeta) é resolvida por `corKeyItem`/`isItemAta` de `src/lib/tipoItemAgenda.ts`, usada em todas as visões, para não quebrar filtros e contagens que dependem de `tipo`.
- GOL publication distribution uses one shared right-side Sheet for individual and bulk actions; destination labels are loaded from coordination records by their stable IDs so renaming stays consistent.
- Projuris attachment imports share byte-level upload progress, bounded workers and serialized batched audit writes; this keeps transfers visible without per-file audit request overhead or unbounded memory usage.
- Projuris creation and recovery share indexed CSV-reference enrichment; unique active CNJ recovery uses an admin-only invoker RPC scoped to audited coordination links, fills only empty fields and audits conflicts; unknown party roles remain labeled observations rather than guessed poles, and recovery batches never delete processes.
- Projuris ZIP matching normalizes paths and Unicode, resolves consolidated parent folders by unique longest path suffix before names, and rejects ambiguity; attachment targets also use unique audited external IDs verified against existing records, so preexisting processes do not appear missing merely because their Projuris field is absent.
- Projuris spreadsheet and backup imports share `classificarTipo`; hearing detection checks the title independently from the source type to prevent source categories or movement history from overriding the title requirement.
- Activity changes, participant additions and charges use one database notification queue for all item types; the channel worker applies each recipient's preferences, includes the actor, and skips sessionless maintenance instead of creating direct in-app alerts.
- Special monitoring (judit-acompanhamento-especial) requests a fresh Judit crawl first and uses the Judit cache only as fallback, because the cache went weeks without updating and hid new movements.
- Special-monitoring email party names are resolved from process fields with fallback to the already-fetched normalized parties, excluding lawyers and third parties; this avoids extra paid requests and preserves registered names.
- DJEN Servidor schedule slots carry a mode in configuracoes_monitoramento_servidor.metadata.modos_horarios (normal|repescagem); repescagem re-runs the last prior day with a normal scheduled run, once per day, because DJEN sometimes indexes publications after the day's last run.
- The "assistente_juridico_geral" role reads all coordinations via dedicated SELECT policies, while edits to tasks, events and hearings are enforced by a DB trigger allowing only items where the user is responsible/involved; the UI uses `podeVerTodasCoordenacoes` only for viewing scope, so security never depends on the screen.

- Control-panel cards show exact open-item counts from the fully loaded unified agenda; while it loads (and only without extra client filters) they show `get_painel_totais` (SECURITY INVOKER) so cards appear immediately. Do not add other parallel legacy summary queries.
- The unified agenda wrapper memoizes its flattened identity-deduplicated items by query data, so unrelated renders do not rebuild every downstream filter and calendar map.
- Calendar indicator queries cache completed ID batches under the same invalidation prefix and user scope as their aggregate query, so loading subsequent agenda pages reuses previous requests without weakening access or mutation refreshes.
- Painel Escritório loads the whole month by coordination only (`escopoEscritorio`: all for admin/assistente geral, else the chosen or user's coordinations, never by responsible/involved people, except Protocolados/Baixados with people chosen, which keep the people filter); the actual reads go through `resolverModoBuscaAgenda`, which calls `get_agenda_pessoal(p_usuario, ...)` for personal views and `get_agenda_escritorio(p_coordenacoes, ...)` for office views one fonte at a time (both STABLE, SECURITY INVOKER), so the browser never sends lists of item identifiers.
- Agenda task and hearing reads never put linked item IDs in `or(...)` or in long `in(...)` lists, because those requests exceeded the server URL limit and made the agenda retry forever; the ready-made searches cover Pessoal and Escritório, and the combinations they do not cover (process/client/origin filters, single-coordination filter, admin "all coordinations" `fetchAll`, incomplete period, several people) keep the old browser queries, which still load linked items in ID batches merged by ID on page 0.
